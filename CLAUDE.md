# CLAUDE.md

Guidance for Claude working in this repo. The documents in `docs/` are the source of truth for what the engine must do. Read the relevant one before changing behavior or interfaces.

## Project

logix-engine is an open source FPGA engine: one Rust binary per platform that exposes FPGA operations as MCP tools over stdin/stdout. Hosts (Logix IDE and other Open Logix frontends, other FPGA tools, IDE extensions, CI, AI agents) launch it as a child process. It drives existing open source tools (Yosys, nextpnr, openFPGALoader and others) and never implements a toolchain itself.

## Code and commands

- `src/main.rs`: the command line. Everything else is a library (`src/lib.rs`), so tests can use it.
- `src/server.rs`: the MCP server (rmcp). `src/tools/`: one file per tool, each with its input and output types and an `EngineTool` impl. Add a tool to `all_definitions()` and `call()` in `src/tools/mod.rs`.
- `src/errors.rs`: the error model. `src/paths.rs`: path checks. `src/logging.rs`: log files, by the org's log layout (the website repo's `CLAUDE.md`, Log files): a session folder per run of the top program (`<yyyymmdd>-<hhmmss>-<pid>`, local time, read once at startup by `init_local_offset`), one file per program named by its chain (`--log-folder`, `--log-name`; `engine.log` at the top), separators, the 10 MB debug cap, and `clean_sessions`, the cleanup policy behind startup cleanup and the `clean_logs` tool (`src/tools/clean_logs.rs`). `src/text.rs`: the text forms. `src/state.rs`: launch settings, engine version, protocol versions, platform.
- `src/packages/`: the package manager. **Remote updates** (the website repo's `CLAUDE.md`, Remote updates, owns the rules; done 2026-11-12): the version folder `remote-config/logix-engine/001/` (the config version is `remote_config::CONFIG_VERSION`): `assign.jsonc` lists the engine releases on each channel (`prod`; every other release is `dev`), and `<channel>-channel.jsonc` names, under `dependencies`, each package's repo, release and file template (a channel without its own file reads `prod-channel.jsonc`), and `latest`, the engine's own newest release on that channel (its repo, release and file; required in `prod-channel.jsonc`, set by the promotion's pull request; `check_updates` reports a newer engine from it as `newer_engine`, its version and release page, which the agent relays to the user, as the tool's description asks; the engine never updates itself (the user's decision, 2026-11-20); `remote_config::newer_release` walks `index.jsonc`'s folders from the largest down to its own, the first with its channel's file); `remote-config/logix-engine/index.jsonc` lists the version folders (names decided 2026-11-20, replacing `channels.jsonc`, `prod.jsonc` and `dev.jsonc`); there's no built-in list. `remote_config.rs` reads it (from `main` on GitHub, or `LOGIX_ENGINE_DEV_REMOTE_CONFIG`, a version folder's URL or a local folder, checked at startup), chooses the channel (`choose_channel`: `LOGIX_ENGINE_CHANNEL`; else, for a release build, its own tag in `assign.jsonc`, `dev` when unlisted; a local build is always `dev`, `IS_RELEASE_BUILD` from `build.rs`'s `LOGIX_ENGINE_BUILD_RELEASE`), reads that channel's file or `prod-channel.jsonc`, resolves it for the platform (SHA-256 from each release's `SHA256SUMS`; the size from the download) (a package's `release` may be `newest`, outside prod and never in `latest`, the user's decision, 2026-11-22, so dev follows the newest pre-release without repinning: `resolve` reads the repo's release feed, `<download base>/<owner>/<repo>/releases.atom` (published releases only, never drafts), and takes its newest date-tagged release, `newest_tag`; not GitHub's API, whose 60 requests an hour per address without a token ran out on CI, HTTP 403, 2026-11-22, then goes on as for a named tag) and caches it in `<engine folder>/remote-config/config.json`, with the build that read it (`reader`: version, release or local build), since another build sharing the engine folder may be on another channel and must read it again (`Cached::matches`; found 2026-11-16); `PackageManager::refresh` reads it again before an operation when it's 24 hours old (`needing_download` calls it), or when a host asks (`download_packages`, `check_updates`), keeps the one in use when reading fails (except the override), deletes packages it no longer names, and the next download replaces the old release. `manifest.rs` is the resolved set's type. Receipts (`logix-download.json`) match release, URL, platform, SHA-256 and `LAYOUT` (raise it only when the package layout changes), not the engine version. To move to a new package release, change the channel's config file by pull request (`dev-channel.jsonc` may name pre-releases; `prod-channel.jsonc` only stable releases); the tests read the repo's folder (`remote_config::repo_file_source`) with the tests' channel (`dev`, or `LOGIX_ENGINE_CHANNEL`), and CI runs them once per config file, so they test what each names. The cache records the channel and the file read; `get_engine_info` reports them (`remote_config`: `channel`, `channel_reason`, `config_file`). `src/progress.rs`: progress by phase. `src/mcp_progress.rs`: sends progress as MCP progress notifications when the request has a progress token, and live tool output as `logix/output` notifications when the request's `_meta` asks for it, both in order before the result. An output line that names a place in one of the request's files gets its `location` (`Display::location` in `src/display_paths.rs`: `file:line[:column]` or yosys's `file:line.column`, only for a file in the source or custom boards folder, named as diagnostics name it; moved from Logix IDE's console links, 2026-11-22, which missed paths with folders). Each tool gets a `Call` with the progress and output sinks and a cancellation token; tools that run programs pass `call.output` to the runner.
- **The engine is the catalog's reader** (the shared rule, website repo's `CLAUDE.md`, 2026-11-08): every Open Logix product, script and agent gets board and FPGA data only through this API, never from Logix Catalog's files (only the catalog repo's own maintenance reads them); for everyone else this API is the intended, supported interface, not enforced (the data is free to use and copy, and reading the files directly is at one's own risk). So what a tool needs from the catalog belongs here, as tool API, and scripts reach it through the command line (see the one-shot command-line mode, docs/requirements.md, open questions).
- `catalog/`: the engine's test data, a copy of **Logix Catalog** (`openlogix/logix-catalog`, its `docs/model.md` is the format; decided 2026-11-08): `boards/<id>.json` (one board each, `$schema` `logix-board-v1.json`), `fpgas/<family>.json` (FPGAs by ID, one file per FPGA family: `ice40`, `ecp5`, `gw1n`, `gw2a`, `gw5a`, `artix7`, `spartan7`, `zynq7000`; the file's name gives their `family`; each names its toolchain's schema, `$schema` `logix-fpgas-<toolchain>-v1.json`, checked by `Catalog::parse`), `schemas/` (`logix-board-v1.json` and the FPGA schemas), and `SOURCE.json` (the commit and its date). **Nothing is built in** (decided 2026-11-10; the pinned catalog and core must fit: `catalog::not_in_core` checks every catalog FPGA against the core's `logix-core.json` `fpgas`, and `tests/build.rs` `the_pinned_catalog_fits_the_pinned_core` runs it on the pair the repo's remote config names, so repin both through the tests): the engine downloads the catalog as the `logix-catalog` package (named by the remote config, about 30 KB, before the core) and reads it at runtime; tools that read boards (`READS_BOARDS` in `src/tools/mod.rs`: every tool whose input names a board, a test checks it; `simulate` and `test` were missing until 2026-11-21, so a client calling one first got "isn't a board in the catalog") load it first (`EngineState::ensure_catalog`, downloading it like any package), and `catalog::get()` returns the loaded one (unit tests read `catalog/`; integration tests call `catalog::use_test_copy()`). **Never edit `catalog/`**: boards are added and fixed in logix-catalog, then `scripts/update-catalog.sh [<ref>]` copies a commit here for the tests. To try a local catalog clone, run the engine with `LOGIX_ENGINE_DEV_CATALOG_FOLDER=<the clone>` (read at startup, a bad folder is an error; `get_engine_info` reports `catalog` with `local: true`). `src/catalog.rs` loads and checks it (`Catalog::parse` takes the board files and the FPGA files); the board schema belongs to logix-catalog (a test validates every board file in `catalog/` against it, and that each reads as a custom board). The catalog has iCE40, ECP5, Gowin and Xilinx (81 boards, 128 variants; the dropped boards and why are in docs/requirements.md). A board is its name (different names are unrelated boards, even with identical hardware; each FPGA size is its own board, since pins can differ); its `variants` list the ways it can be programmed (one concept: there are no separate configurations), the first being the default (flash wherever the board has it, checked by a test), each with a `selector`, `{"connection": …, "memory": …}` (no variant IDs: the selector names the variant, and `board_variant` in requests is a selector; no two of a board's variants have the same one), whose values are the two standard dimensions every board has ( from the engine's list `STANDARD_DIMENSIONS` with labels and help; `get_catalog` adds the board's derived `dimensions`; `unspecified` connection when unknown; memory follows from the command), the programmer, `args`, `usb` and its own `tested` (false only when its programming changed from the original command and wasn't tried on hardware, or it's new; a change rated low risk, checked in the programmer's source, keeps it true, such as `--busdev-num ${BUS}:${DEV}` on every FTDI openFPGALoader command and `-p ${USB_PATH}` on every dfu-util command, which tests check), optional `user_notes` (for users: warnings and missing information, such as a USB filter that matches other boards) and `maintainer_notes` (for maintainers: where settings come from and why they changed; never returned by `get_catalog`; never required). A variant changes only how the board is programmed: all variants of a board have the same FPGA and the same pin file (a version with an LED or any signal on another pin is a different board); tools take an optional `board_variant` (some or all of a selector, `VariantChoice`: the board's first variant with those values is used; `build` reports the full selector used; each catalog variant has a `label`, such as "USB · Flash"); a different variant doesn't rebuild: builds and uploads compare only the FPGA's build settings (`FpgaDefinition::build_key`; the list is in docs/tool-api.md, What counts as the same board), and the build record takes the request's board, variant included. The rules are in docs/requirements.md, Boards and board variants. The engine supports the programmers in `PROGRAMMERS` (openfpgaloader, iceprog, dfu-util, icesprog; all from oss-cad-suite). Never write "Apio" in catalog data. **Never run a programmer by hand to see its messages while a board it could reach is connected**: icesprog wrote to the user's iCESugar-Pro that way.
- **FPGA families and toolchains** (decided 2026-11-08; the website repo's `CLAUDE.md` owns the rule): people see **families**, the names on the chips (`catalog::Family`: iCE40, ECP5, GW1N, GW2A, GW5A, Artix-7, Spartan-7, Zynq-7000), and every FPGA definition has one, from its catalog file's name. Each family maps to one **toolchain** (`catalog::Toolchain`: `ice40`, `ecp5`, `gowin`, `openxc7`), which selects the build flow, the pin file format, the simulation models and the I/O standards, and is for logs, diagnostics and the API (`get_catalog` `families` gives each family's), never the main word people see. What a family implies (yosys's Gowin `-family`, the Project X-Ray folder, `synth_xilinx -arch xc7`) is derived from it (`Family::yosys_family`, `Family::prjxray_family`), not kept in the catalog. Don't use the word "architecture" for either.
- FPGAs in `catalog/fpgas/` have a `jtag_idcode` (ECP5, Gowin, Xilinx), taken from openFPGALoader 1.2.0's `src/part.hpp` by part number (Gowin by `packer_device`), never by size; a test checks every JTAG board's FPGA has one. Before writing over JTAG, `program_board` runs openFPGALoader `--detect` with only the variant's connection options (`CONNECTION_OPTIONS` in `src/program.rs`, so it can't write) and refuses another FPGA. Update the ID codes when the openFPGALoader version changes.
- `src/display_paths.rs`: the request's `display_paths` (how paths read for people; docs/tool-api.md, Display paths): files first, then folders, the first match wins, matched by real location; then the request's own paths as it gave them. Applied in `tools::call` to every result (diagnostics' `file` and `text`, `message`, `details`, `output`; never `commands` or path fields) and to the live output (`DisplayOutput`; never command lines); tools use `Call::display` only for text they write elsewhere (the diagram's source places). Diagnostics name files as the request gave them: source files relative to the source folder, custom board files by the folder as given plus their names.
- `src/tools/compare_boards.rs`: the `compare_boards` tool: what differs between two boards (board IDs only: variants never change it) as structured aspects (always all, in a fixed order, each `yes`, `no` or `unknown` when the catalog doesn't describe it yet, with `from` and `to` of any JSON type per aspect), plus `same_build`; facts only, never advice, so it serves any project model. New catalog facts become aspects or settle `unknown` ones: `clock` (MHz list) and `leds` (count) come from `resources`.
- Board `resources` (`src/resources.rs`, `catalog::Resources`: a map put in type order as it's read, clocks first and each type in the file's order (`in_type_order`, the user's request, 2026-11-19), for readable results the same in every frontend, though the order means nothing (docs/tool-api.md; never pick a resource by position); serde_json's `preserve_order` feature keeps it, since board files are read through `serde_json::Value`, port name to `Resource`, a serde enum tagged by `type`, each type with its own fields: `clock` (pin, mhz), `leds`/`buttons`/`switches` (pins, active), `rgb_led` (red, green, blue), `led_matrix` (leds, colors), `uart`, `pmod` (8 pins), `header`, `unclassified`; every type may have `io_standard`, `source`, `requires`, `user_notes`, and `ai_hints` last (`resources::AiHints`: lines of free text for AI agents writing designs, checked by `ai_hints_problems` like the catalog's schema, never read by tools; boards have it too, also last; docs/tool-api.md, AI hints); boards and resources may have `requires` (`resources::Requirement`: `drive`, pins a design must drive to a level, or `setup`, something a person does, such as a jumper; checked by `board_requires_problems` and `problems`); checked by `resources::problems` for the catalog and custom boards: port names, a pin twice in one resource, PMOD pin count, clock frequency, the I/O standard for the FPGA family). `get_catalog` adds words for people (moved from Logix IDE's Board Explorer, 2026-11-22): each resource's `type_label`, `pins_text` and `notes_text` (`Resource::with_texts`) and each drive's `text` (`Requirement::with_text`), output-only fields, placed before `ai_hints`, that a board file sets only as a problem (`resources::problems`; not `skip_deserializing`, which would leave them out of the output schema too); each FPGA's `label` (`CatalogFpga`, flattening the definition); each family's `constraint_comment` (`#`, or `//` for Gowin's `.cst`). `get_engine_info`'s `hdl_extensions` gives the source and include extensions (`format::SOURCE_EXTENSIONS`, `INCLUDE_EXTENSIONS`). Its `language_server` gives Verible's language server as `command` (absolute path), `args` (`--ruleset=none --lsp_enable_hover=true`, Logix IDE's) and `env` (empty), from a ready core's `verible` component (2026-11-22, meeting docs/requirements.md's "returns the tool's command and environment"). One pin gives a plain port, several a vector, bit 0 first. For creating designs and pin files (blinky); builds never use them. Resources may share pins.
- `src/board.rs`: boards in requests: `board` is an ID, and every board tool takes the same `custom_boards_folder` (read by `src/custom_boards.rs`: a folder of board files, one board each in the catalog's format, named `<id>.json`, other files ignored; the FPGA always a catalog `fpga_id` (custom boards add boards and their programming, never FPGAs, the user's decision, 2026-11-07); every problem a diagnostic at file, line and column, located by `src/json_pos.rs`; a problem stops every board tool, except `list_devices` without a build folder, which matches against the catalog only and returns the error in `custom_boards_problem` (2026-11-22, so device scans keep working while the user fixes the file); each board and variant read on its own, so problems come all at once, by file then line, at most `MAX_PROBLEMS` (10) plus an `info` note with how many more; invalid JSON is one problem; a custom board replaces the catalog board with its ID; `known_boards`, `resolve`), resolved into the full board the build record keeps; `program_board` refuses an upload whose board changed since the build. `build` with `lint: true` runs `lint` first, as Logix IDE's Verify did (moved here 2026-11-22): lint never stops the build, and `diagnostics` (and a design error's) has lint's problems first, then the build's without those at a line and severity lint already reported (`merge_diagnostics` in `src/tools/build.rs`; progress on one scale through a `Stage` sink per step). `src/build/`: the build (each toolchain's standard open source flow: yosys, nextpnr-ice40 and icepack for iCE40; yosys, nextpnr-ecp5 and ecppack for ECP5; yosys, nextpnr-himbaechel and gowin_pack for Gowin; yosys, then nextpnr-xilinx, fasm2frames and xc7frames2bit from the `openxc7` package, for Xilinx), up-to-date check, build record, and `clean.rs` for `clean_build`. `src/build/parse.rs` reads tool output into diagnostics; its tests use real tool output. `src/sim/`: lint (Verilator), testbenches (`testbench.rs`: iverilog and vvp, for test and simulate) with the standard options and the FPGA's primitive models; `src/sim/parse.rs` reads Verilator and Icarus output into diagnostics, tested with real output. Testbench results have `ending_text` for the endings the engine causes or that need explaining (`Ending::text`: timeout, sim_time_limit, no_finish; moved from Logix IDE, 2026-11-22). `src/format.rs`: the `format` tool's work (Verible's formatter in place; its tests use real Verible output). `src/diagram/`: the `diagram` tool's work (decided with the user from a prototype, 2026-11-11): yosys writes the design's netlist (the FPGA's primitive models read as black boxes, so their ports have directions), `rules.rs` applies the prototype's rules (labels for clocks and resets that go to two or more places and for fixed values, no memory initialization blocks, plain names, registers named after their signal) and builds the model, `schematic.rs` adds netlistsvg's constants, bus splits and joins and wires and draws the SVG, `symbols.rs` has the symbols (netlistsvg's skin as the prototype changed it), `layout.rs` runs logix-core's `elkjs` in QuickJS (rquickjs) in a worker process (the engine itself with the hidden `--diagram-layout-worker`, one graph per line; killed on timeout or cancel, never interrupted, since interrupting QuickJS mid-layout corrupted its memory and aborted the engine, 2026-11-11; tests point it at the engine binary with `set_worker_program`), and `viewer.html` is the page's template (self-contained: no network, no outside resources; AI agents open it for users with `open`). The SVG has no script; its scoped default style (`diagram.css`) uses `--logix-diagram-*` variables. Change the look and rules there, not in frontends. Results of `lint`, `test`, `simulate`, `format`, `diagram` and `build` list `checked_files` (`tools::checked_files`: the listed files, their includes, then the constraint file; a design error has them in `data.checked_files`, `tools::with_checked`; named by display paths), so hosts replace exactly those files' old problems (moved from Logix IDE's `taskReads`, 2026-11-22). `src/commands.rs`: the `commands` list in results (each program run, with a shell line that reruns it); `run_watched` and `program_board` record into `Call::commands`. `src/runner.rs` runs tools with a minimal environment and stops the process tree on cancel (SIGTERM, then SIGKILL after 2 s); it splits output on `\n`, `\r\n` and bare `\r`, marks lines a bare `\r` ended as `redraw` (sent in `logix/output`). `src/output_rules.rs`: the output rules, one table of everything known about how particular tools print (hide, level, rewrite, note, progress phase, percentage), applied to every tool run's live output and progress through `ToolOutput` (in `run_watched` and `program_board`); never to results or diagnostics; each rule with its source and real lines it must match and must not, checked by tests. Add tool-specific output knowledge there, never in frontends.

## CI and releases

**Repo type: installable** (`.github/logix-repo-metadata.jsonc`; the website repo's `CLAUDE.md`, Repo types, owns the policy): people install the engine for AI agents, and Logix IDE also downloads it as a dependency; a repo that's both is installable.

Same conventions as logix-ide, using the shared actions from `openlogix/.github` (`openlogix/.github/actions/<name>@main`; that repo documents and tests them).

- **`test.yaml`**: a `remote-config` job (Ubuntu) runs the shared `check-remote-config` action on `remote-config/` (platforms `darwin-arm64`, `windows-x86-64` and `linux-x86-64`); a `channels` job (Ubuntu) lists the channels with the shared `list-config-channels` action, one per config file in the newest version folder (so `prod` alone in normal maintenance, and `dev` too while `dev-channel.jsonc` exists); then the tests, one job per OS version and channel (`test (macos-15, prod)`): matrix `os` macos-15, macos-26, windows-2025, ubuntu-22.04 and ubuntu-24.04 (named explicitly, a new one added when GitHub ships it; not macos-latest, which is one of them) × `channel` from that list, `fail-fast: false`, 60 min (a job takes about 5; the room is for slow runners or mirrors, as Logix IDE's apt mirror on 2026-11-18), bash on every OS (Git's bash on Windows). Strict (the website repo's `CLAUDE.md`, Strict CI): every job is required. On every push and pull request, manually, and daily at 00:00 UTC; a newer run for the same ref cancels the older one. Installs the pinned Rust, then runs `scripts/test.sh` with `LOGIX_ENGINE_CHANNEL` set to the job's channel. Tests that serve their own config (`tests/packages.rs`) use that channel's file, so they pass on any channel.
- **`build-pre-release.yaml`** (on every push to `main`, daily at 00:00 UTC, and manually; a newer run cancels a running one), three jobs:
  - `prepare` (Ubuntu): the shared `start-pre-release` action (today's tags, the stable-release check, `BUILD-INFO.json` as the `build-info` artifact, with `config-version`, read from `remote_config::CONFIG_VERSION`, as an extra field: `repos-janitor` finds the releases a Latest engine uses by it). The release tag is the engine version.
  - `build-darwin-arm64` (reusable `build-darwin-arm64.yaml`, macos-latest): `read-build-info` with the platform, checks out exactly `repo-commit` into `_repo/`, runs `scripts/test.sh`, builds with `LOGIX_ENGINE_BUILD_VERSION` = the release tag, packs `logix-engine-darwin-arm64-<package tag>.tgz` (one `logix-engine/` folder with the binary, `LICENSE-MIT` and `LICENSE-APACHE`), and checks that the packed binary reports the release tag and has an ad-hoc signature.
  - `build-windows-x86-64` (reusable `build-windows-x86-64.yaml`, windows-2025, Git's bash; Milestone 3): the same for `logix-engine-windows-x86-64-<package tag>.tgz` with `logix-engine.exe` (`check-platform` with `os: msys`, Git's bash's name), without the signature check. Strict: its tests must pass, and `pre-release` waits for it.
  - `build-linux-x86-64` (reusable `build-linux-x86-64.yaml`, ubuntu-22.04 for an older glibc; Milestone 4): the same for `logix-engine-linux-x86-64-<package tag>.tgz`. Strict since Linux's promotion: `pre-release` waits for all three platforms.
  - `pre-release` (Ubuntu): `read-build-info`, downloads the packages, virus scan, writes the release's own content, in the same structure as Logix IDE's (the user's request, 2026-11-15): what the engine is, then one section per platform, each with its download link, its steps (macOS: `xattr -c`; Windows: `Unblock-File`; Linux: plain `tar`), `--version`, `claude mcp add` and how to uninstall, with a line before, between and after the sections, then the shared `publish-pre-release` action writes the standard release text around it, makes the day's pre-release again from scratch with the `.tgz`, `BUILD-INFO.json` and `SHA256SUMS`, and deletes old pre-releases by the shared policy.

## Rules that are easy to break

- **stdout is only for MCP.** Logs and tool output go to the log file and stderr, never stdout.
- **The tool API and command line never break** after the first release. Changes only add tools, optional fields or arguments. A breaking change gets a new tool name.
- **Stateless requests.** Every request carries its own folders and board. The engine never reads host project files or merges catalog definitions from disk, except the source files and the custom boards folder a request names. Requests never carry source text.
- **Safe file changes.** Check the path keyword rules, resolve symbolic links, and refuse forbidden locations before any disk change. The engine writes only in the engine folder and build folders, plus in-place rewrites of named source files when an operation calls for it, such as formatting. It creates no other files in the source folder.
- **Build folders are disposable.** Deleting one never loses data, and the next operation that writes to it creates it again, with the same result. Never keep anything in a build folder that can't be generated again. A test checks a rebuild after a delete.
- **Match criteria are internal.** How a device's match level is decided never appears in the tool API, tool descriptions or messages to hosts, and can change in any version. Hosts get only the level (and later, an explanation for people to read as is).
- **Errors are data.** Use the six error categories and the suggested action codes from the tool API. A failing test or missed timing is a result, not an error. Messages never assume a particular host.
- **Schemas come from Rust types.** Don't hand-write JSON schemas. Every tool and field needs a clear, self-contained description, because AI agents learn the tools from them alone.
- **No network at startup, no unreported upgrades** (decided 2026-11-12, for remote updates). Network access happens only before an operation that needs packages, to fetch the engine's remote config when its cached copy is more than 24 hours old and to download or repair packages, or when a host asks (`check_updates`). An update is reported in the operation's progress and result, and `get_engine_info` lists the releases in use. `--no-auto-download` turns all of it off. The org rules are in the website repo's `CLAUDE.md`, Remote updates.
- **Development never affects end users** (the website repo's `CLAUDE.md`, the user's requirement for Milestone 2, 2026-11-12): try a remote config change with `LOGIX_ENGINE_DEV_REMOTE_CONFIG` (a branch's file, a fork or a local file), never by changing `remote-config/` on `main`, which every installed engine reads; it reaches users only by a pull request merged with CI green. A developer's own engine folders may be shared between dev and regular runs.
- **Date versions.** The engine follows the Open Logix versioning rule (the website repo's `CLAUDE.md`, Remote updates, Versions and tags): `yyyy-mm-dd` for tags and pins, `yyyymmdd` only in file names, `yyyy.mm.dd` for the version people see, semver (`2026.5.7`) only where a tool requires it, and at most one release a day. Compare by date, never as mixed-form strings.

## A reference for frontends

The Logix IDE is the reference frontend: the rule is in the website repo's `CLAUDE.md` (shared Open Logix rules). For the engine this means: logic every frontend would need, that doesn't depend on a frontend's own model, belongs here, such as FPGA family names (`get_catalog` families) plain resource names (`build` `resources_summary`), resource descriptions and checked shares (`build` `resources`, `src/build/descriptions.rs`; a share is null when nextpnr's numbers aren't valid, as Apio's report), clock names (`build` `clocks_summary`) and the build report's text (`build` `report` and `report_summary`, 2026-11-10; frontends show it as is). When the IDE has to repeat engine knowledge, that is an engine gap: fill it here and have the IDE use it. The tool API stands on its own for frontends outside Open Logix, and its "Recipes for frontend developers" point to the IDE files that implement each recipe.

**Canonical board** (the website repo's `CLAUDE.md` owns the rule, 2026-11-10): the engine's docs, tool descriptions and examples use the iCESugar v1.5 (`icesugar-1-5`) as their example board; the engine itself never favors it (catalog order, matching, defaults), except to break a tie. Examples that show captured hardware output, such as `list_devices` on an Alhambra II, stay as captured until they're captured again on an iCESugar. The tutorial (`docs/tutorial-claude-code.md`) uses the iCESugar v1.5 too (moved 2026-11-11, the user's decision, before the team had the board: its prompts are still to be tried on one). ## How work is done here

The human directs the work and tests the results. Claude writes and maintains the code, the tests and the docs. Humans don't review every line, so:

- Add or update tests with every change. Tests are the main guard against regressions.
- Keep external interfaces, requirements and docs simple and easy for people to understand. Code readability matters less than correctness and test coverage.
- Update the docs in `docs/` in the same change as the code they describe. If code and docs disagree, ask which one is right.
- Record open questions in the relevant doc's "Open questions" section, or as a GitHub issue if the user asks.
