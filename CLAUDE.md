# CLAUDE.md

Guidance for Claude working in this repo. The documents in `docs/` are the source of truth for what the engine must do. Read the relevant one before changing behavior or interfaces.

## Project

logix-engine is an open source FPGA engine: one Rust binary per platform that exposes FPGA operations as MCP tools over stdin/stdout. Hosts (Logix IDE and other Open Logix frontends, other FPGA tools, IDE extensions, CI, AI agents) launch it as a child process. It drives existing open source tools (Yosys, nextpnr, openFPGALoader and others) and never implements a toolchain itself.

## Current scope: Milestone 2

Milestone 1 (iCE40, seven tools, tested on an Alhambra II) is done. Milestone 2 is Logix IDE running on the engine without losing any feature it had (its "Still to do" list, under Table 15: the features are done; macOS first, so it also takes remote updates, a topic to decide with the user, 2026-11-11): Table 15 in [docs/requirements.md](docs/requirements.md#acceptance-and-phasing) lists them (lint, test, simulate, format, diagram, live tool output, and every board the IDE offers today across all four toolchains; a board is dropped only for a very good, recorded reason). Examples aren't an engine feature: an example is a project, and project models are defined by the frontends, not the engine, so each frontend provides examples in its own model and source format. For AI sessions with no other requirements, the engine only suggests a default one (docs/tool-api.md, Default project model; a short form is in the server instructions in `src/server.rs`). It isn't a standard for frontends and hosts, and the engine needs no project file in any format. macOS arm64 only: Milestone 3 brings the engine and Logix IDE to Windows x64, Milestone 4 to Linux x64 (decided 2026-11-10; docs/requirements.md, Acceptance and phasing). Toolchain packages come from existing open source package releases, pinned in the manifest. Don't build later-phase features unless asked.

## Code and commands

- `src/main.rs`: the command line. Everything else is a library (`src/lib.rs`), so tests can use it.
- `src/server.rs`: the MCP server (rmcp). `src/tools/`: one file per tool, each with its input and output types and an `EngineTool` impl. Add a tool to `all_definitions()` and `call()` in `src/tools/mod.rs`.
- `src/errors.rs`: the error model. `src/paths.rs`: path checks. `src/logging.rs`: log files. `src/text.rs`: the text forms. `src/state.rs`: launch settings, engine version, protocol versions, platform.
- `src/packages/`: the package manager. **Remote updates** (the website repo's `CLAUDE.md`, Remote updates, owns the rules; done 2026-11-12): `remote-config/logix-engine/config-001.jsonc` (the config version is `remote_config::CONFIG_VERSION`) names each package's repo, release and file template; there's no built-in list. `remote_config.rs` reads it (from `main` on GitHub, or `LOGIX_ENGINE_DEV_REMOTE_CONFIG`, a URL or a local file, checked at startup), resolves it for the platform (SHA-256 from each release's `SHA256SUMS`; the size from the download) and caches it in `<engine folder>/remote-config/config.json`; `PackageManager::refresh` reads it again before an operation when it's 24 hours old (`needing_download` calls it), or when a host asks (`download_packages`, `check_updates`), keeps the one in use when reading fails (except the override), deletes packages it no longer names, and the next download replaces the old release. `manifest.rs` is the resolved set's type. Receipts (`logix-download.json`) match release, URL, platform, SHA-256 and `LAYOUT` (raise it only when the package layout changes), not the engine version. To move to a new package release, change the config file by pull request (pre-releases allowed during development, repinned as they expire); the tests read the repo's file (`remote_config::repo_file_source`), so they test what it names. `src/progress.rs`: progress by phase. `src/mcp_progress.rs`: sends progress as MCP progress notifications when the request has a progress token, and live tool output as `logix/output` notifications when the request's `_meta` asks for it, both in order before the result. Each tool gets a `Call` with the progress and output sinks and a cancellation token; tools that run programs pass `call.output` to the runner.
- **The engine is the catalog's reader** (the shared rule, website repo's `CLAUDE.md`, 2026-11-08): every Open Logix product, script and agent gets board and FPGA data only through this API, never from Logix Catalog's files (only the catalog repo's own maintenance reads them); for everyone else this API is the intended, supported interface, not enforced (the data is free to use and copy, and reading the files directly is at one's own risk). So what a tool needs from the catalog belongs here, as tool API, and scripts reach it through the command line (see the one-shot command-line mode, docs/requirements.md, open questions).
- `catalog/`: the engine's test data, a copy of **Logix Catalog** (`openlogix/logix-catalog`, its `docs/model.md` is the format; decided 2026-11-08): `boards/<id>.json` (one board each, `$schema` `logix-board-v1.json`), `fpgas/<family>.json` (FPGAs by ID, one file per FPGA family: `ice40`, `ecp5`, `gw1n`, `gw2a`, `gw5a`, `artix7`, `spartan7`, `zynq7000`; the file's name gives their `family`; each names its toolchain's schema, `$schema` `logix-fpgas-<toolchain>-v1.json`, checked by `Catalog::parse`), `schemas/` (`logix-board-v1.json` and the FPGA schemas), and `SOURCE.json` (the commit and its date). **Nothing is built in** (decided 2026-11-10; the pinned catalog and core must fit: `catalog::not_in_core` checks every catalog FPGA against the core's `logix-core.json` `fpgas`, and `tests/build.rs` `the_pinned_catalog_fits_the_pinned_core` runs it on the pair the repo's remote config names, so repin both through the tests): the engine downloads the catalog as the `logix-catalog` package (named by the remote config, about 30 KB, before the core) and reads it at runtime; tools that read boards (`get_catalog`, `compare_boards`, `build`, `lint`, `list_devices`, `program_board`) load it first (`EngineState::ensure_catalog`, downloading it like any package), and `catalog::get()` returns the loaded one (unit tests read `catalog/`; integration tests call `catalog::use_test_copy()`). **Never edit `catalog/`**: boards are added and fixed in logix-catalog, then `scripts/update-catalog.sh [<ref>]` copies a commit here for the tests. To try a local catalog clone, run the engine with `LOGIX_ENGINE_DEV_CATALOG_FOLDER=<the clone>` (read at startup, a bad folder is an error; `get_engine_info` reports `catalog` with `local: true`). `src/catalog.rs` loads and checks it (`Catalog::parse` takes the board files and the FPGA files); the board schema belongs to logix-catalog (a test validates every board file in `catalog/` against it, and that each reads as a custom board). The catalog has iCE40, ECP5, Gowin and Xilinx (81 boards, 128 variants; the dropped boards and why are in docs/requirements.md). A board is its name (different names are unrelated boards, even with identical hardware; each FPGA size is its own board, since pins can differ); its `variants` list the ways it can be programmed (one concept: there are no separate configurations), the first being the default (flash wherever the board has it, checked by a test), each with a `selector`, `{"connection": …, "memory": …}` (no variant IDs: the selector names the variant, and `board_variant` in requests is a selector; no two of a board's variants have the same one), whose values are the two standard dimensions every board has ( from the engine's list `STANDARD_DIMENSIONS` with labels and help; `get_catalog` adds the board's derived `dimensions`; `unspecified` connection when unknown; memory follows from the command), the programmer, `args`, `usb` and its own `tested` (false only when its programming changed from the original command and wasn't tried on hardware, or it's new; a change rated low risk, checked in the programmer's source, keeps it true, such as `--busdev-num ${BUS}:${DEV}` on every FTDI openFPGALoader command and `-p ${USB_PATH}` on every dfu-util command, which tests check), optional `user_notes` (for users: warnings and missing information, such as a USB filter that matches other boards) and `maintainer_notes` (for maintainers: where settings come from and why they changed; never returned by `get_catalog`; never required). A variant changes only how the board is programmed: all variants of a board have the same FPGA and the same pin file (a version with an LED or any signal on another pin is a different board); tools take an optional `board_variant` (some or all of a selector, `VariantChoice`: the board's first variant with those values is used; `build` reports the full selector used; each catalog variant has a `label`, such as "USB · Flash"); a different variant doesn't rebuild: builds and uploads compare only the FPGA's build settings (`FpgaDefinition::build_key`; the list is in docs/tool-api.md, What counts as the same board), and the build record takes the request's board, variant included. The rules are in docs/requirements.md, Boards and board variants. The engine supports the programmers in `PROGRAMMERS` (openfpgaloader, iceprog, dfu-util, icesprog; all from oss-cad-suite). Never write "Apio" in catalog data. **Never run a programmer by hand to see its messages while a board it could reach is connected**: icesprog wrote to the user's iCESugar-Pro that way.
- **FPGA families and toolchains** (decided 2026-11-08; the website repo's `CLAUDE.md` owns the rule): people see **families**, the names on the chips (`catalog::Family`: iCE40, ECP5, GW1N, GW2A, GW5A, Artix-7, Spartan-7, Zynq-7000), and every FPGA definition has one, from its catalog file's name. Each family maps to one **toolchain** (`catalog::Toolchain`: `ice40`, `ecp5`, `gowin`, `openxc7`), which selects the build flow, the pin file format, the simulation models and the I/O standards, and is for logs, diagnostics and the API (`get_catalog` `families` gives each family's), never the main word people see. What a family implies (yosys's Gowin `-family`, the Project X-Ray folder, `synth_xilinx -arch xc7`) is derived from it (`Family::yosys_family`, `Family::prjxray_family`), not kept in the catalog. Don't use the word "architecture" for either.
- FPGAs in `catalog/fpgas/` have a `jtag_idcode` (ECP5, Gowin, Xilinx), taken from openFPGALoader 1.2.0's `src/part.hpp` by part number (Gowin by `packer_device`), never by size; a test checks every JTAG board's FPGA has one. Before writing over JTAG, `program_board` runs openFPGALoader `--detect` with only the variant's connection options (`CONNECTION_OPTIONS` in `src/program.rs`, so it can't write) and refuses another FPGA. Update the ID codes when the openFPGALoader version changes.
- `src/display_paths.rs`: the request's `display_paths` (how paths read for people; docs/tool-api.md, Display paths): files first, then folders, the first match wins, matched by real location; then the request's own paths as it gave them. Applied in `tools::call` to every result (diagnostics' `file` and `text`, `message`, `details`, `output`; never `commands` or path fields) and to the live output (`DisplayOutput`; never command lines); tools use `Call::display` only for text they write elsewhere (the diagram's source places). Diagnostics name files as the request gave them: source files relative to the source folder, custom board files by the folder as given plus their names.
- `src/tools/compare_boards.rs`: the `compare_boards` tool: what differs between two boards (board IDs only: variants never change it) as structured aspects (always all, in a fixed order, each `yes`, `no` or `unknown` when the catalog doesn't describe it yet, with `from` and `to` of any JSON type per aspect), plus `same_build`; facts only, never advice, so it serves any project model. New catalog facts become aspects or settle `unknown` ones: `clock` (MHz list) and `leds` (count) come from `resources`.
- Board `resources` (`src/resources.rs`, `catalog::Resources`: a map that keeps the file's order for readable results, though the order means nothing (docs/tool-api.md; never pick a resource by position); serde_json's `preserve_order` feature keeps it, since board files are read through `serde_json::Value`, port name to `Resource`, a serde enum tagged by `type`, each type with its own fields: `clock` (pin, mhz), `leds`/`buttons`/`switches` (pins, active), `rgb_led` (red, green, blue), `led_matrix` (leds, colors), `uart`, `pmod` (8 pins), `header`, `unclassified`; every type may have `io_standard`, `source`, `requires`, `user_notes`, and `ai_hints` last (`resources::AiHints`: lines of free text for AI agents writing designs, checked by `ai_hints_problems` like the catalog's schema, never read by tools; boards have it too, also last; docs/tool-api.md, AI hints); boards and resources may have `requires` (`resources::Requirement`: `drive`, pins a design must drive to a level, or `setup`, something a person does, such as a jumper; checked by `board_requires_problems` and `problems`); checked by `resources::problems` for the catalog and custom boards: port names, a pin twice in one resource, PMOD pin count, clock frequency, the I/O standard for the FPGA family). One pin gives a plain port, several a vector, bit 0 first. For creating designs and pin files (blinky); builds never use them. Resources may share pins.
- `src/board.rs`: boards in requests: `board` is an ID, and every board tool takes the same `custom_boards_folder` (read by `src/custom_boards.rs`: a folder of board files, one board each in the catalog's format, named `<id>.json`, other files ignored; the FPGA always a catalog `fpga_id` (custom boards add boards and their programming, never FPGAs, the user's decision, 2026-11-07); every problem a diagnostic at file, line and column, located by `src/json_pos.rs`; each board and variant read on its own, so problems come all at once, by file then line, at most `MAX_PROBLEMS` (10) plus an `info` note with how many more; invalid JSON is one problem; a custom board replaces the catalog board with its ID; `known_boards`, `resolve`), resolved into the full board the build record keeps; `program_board` refuses an upload whose board changed since the build. `src/build/`: the build (each toolchain's standard open source flow: yosys, nextpnr-ice40 and icepack for iCE40; yosys, nextpnr-ecp5 and ecppack for ECP5; yosys, nextpnr-himbaechel and gowin_pack for Gowin; yosys, then nextpnr-xilinx, fasm2frames and xc7frames2bit from the `openxc7` package, for Xilinx), up-to-date check, build record, and `clean.rs` for `clean_build`. `src/build/parse.rs` reads tool output into diagnostics; its tests use real tool output. `src/sim/`: lint (Verilator), testbenches (`testbench.rs`: iverilog and vvp, for test and simulate) and GTKWave (`gtkwave.rs`: default layouts, detached launch), with the standard options and the FPGA's primitive models; `src/sim/parse.rs` reads Verilator and Icarus output into diagnostics, tested with real output. `src/format.rs`: the `format` tool's work (Verible's formatter in place; its tests use real Verible output). `src/diagram/`: the `diagram` tool's work (decided with the user from a prototype, 2026-11-11): yosys writes the design's netlist (the FPGA's primitive models read as black boxes, so their ports have directions), `rules.rs` applies the prototype's rules (labels for clocks and resets that go to two or more places and for fixed values, no memory initialization blocks, plain names, registers named after their signal) and builds the model, `schematic.rs` adds netlistsvg's constants, bus splits and joins and wires and draws the SVG, `symbols.rs` has the symbols (netlistsvg's skin as the prototype changed it), `layout.rs` runs logix-core's `elkjs` in QuickJS (rquickjs) in a worker process (the engine itself with the hidden `--diagram-layout-worker`, one graph per line; killed on timeout or cancel, never interrupted, since interrupting QuickJS mid-layout corrupted its memory and aborted the engine, 2026-11-11; tests point it at the engine binary with `set_worker_program`), and `viewer.html` is the page's template (self-contained: no network, no outside resources; AI agents open it for users with `open`). The SVG has no script; its scoped default style (`diagram.css`) uses `--logix-diagram-*` variables. Change the look and rules there, not in frontends. `src/commands.rs`: the `commands` list in results (each program run, with a shell line that reruns it); `run_watched` and `program_board` record into `Call::commands`. `src/runner.rs` runs tools with a minimal environment and stops the process tree on cancel (SIGTERM, then SIGKILL after 2 s); it splits output on `\n`, `\r\n` and bare `\r`, marks lines a bare `\r` ended as `redraw` (sent in `logix/output`). `src/output_rules.rs`: the output rules, one table of everything known about how particular tools print (hide, level, rewrite, note, progress phase, percentage), applied to every tool run's live output and progress through `ToolOutput` (in `run_watched` and `program_board`); never to results or diagnostics; each rule with its source and real lines it must match and must not, checked by tests. Add tool-specific output knowledge there, never in frontends.
- `src/devices.rs`: USB scanning with libusb built in (rusb, vendored), device IDs (opaque, from the USB port path), the device's release (`bcdDevice`, read raw through libusb; on FTDI chips and debuggers that act like them it tells the chip type, and filters may require it), board matching with a match level, `strong`, `possible` or `weak` (`MatchLevel`: what the match means for the user, never its cause; hosts only show and compare levels; the criteria, including `FACTORY_DEFAULT_NAMES` and `FEW_BOARDS`, are internal and may change without notice, kept in docs/requirements.md for maintainers and never in the tool API; against the catalog and the request's custom boards, at request time) and finding the chosen device; `program_board` requires a device ID from `list_devices`. `src/program.rs`: programmer commands, progress from programmer output, and failure classification, tested with the programmers' real messages. `list_devices` and `program_board` take the scan as a parameter (`run_with`), so tests use fake device lists and a fake programmer; real boards are checked by hand.
- `build.rs` sets the engine version, `yyyy.mm.dd`: from the `LOGIX_ENGINE_BUILD_VERSION` env var for releases (the release tag, `yyyy-mm-dd`), otherwise today's UTC date. Versions shown to people (`get_engine_info`, messages, the `package` of a command) use `manifest::shown_version`; release tags, pins and folder names stay `yyyy-mm-dd`. The release workflow writes the semver form (`2026.5.7`) into `Cargo.toml` and `Cargo.lock` before building.
- **Data folders** (the website repo's `CLAUDE.md`; decided 2026-11-10): each Open Logix program keeps its data in its own folder in `~/.logix`, with its own engine folder (hosts don't share one). The tutorial and the release notes use `~/.logix/claude-code/engine`; this repo's dev scripts use `~/.logix/engine-dev/` (`bin/`, the engine copy a session runs; `engine/`, its engine folder; `playground/`, where Claude or Grok works). Logix IDE uses `~/.logix/ide/engine`.
- Environment variables follow the Open Logix naming scheme (website repo's `CLAUDE.md`). This repo's: `LOGIX_ENGINE_BUILD_VERSION` (build), and for the dev scripts `LOGIX_ENGINE_DEV_FOLDER`, `LOGIX_ENGINE_DEV_LOG_LEVEL`, `LOGIX_ENGINE_DEV_PLAYGROUND`, `LOGIX_ENGINE_DEV_BIN_FOLDER`. The engine binary itself reads two, at startup (docs/command-line.md, Diagnostic settings): `LOGIX_ENGINE_DEV_REMOTE_CONFIG`, a remote config to read instead of its own (a URL or a local file; a bad value stops the engine, and failing to read it is an error, never a fallback), and `LOGIX_ENGINE_DEV_CATALOG_FOLDER`, a catalog folder (a logix-catalog clone) to read instead of the downloaded `logix-catalog` package, a diagnostic setting (a bad folder stops the engine; the tests' MCP sessions use it with `catalog/`). (`LOGIX_SIM` is a Verilog macro, not an environment variable.)
- Tests: unit tests next to the code; `tests/cli.rs` (command line), `tests/mcp.rs` (end to end: launches the binary and talks MCP), `tests/schemas.rs` (published schemas), `tests/packages.rs` (package download against a local test server), `tests/build.rs` (real builds with the real toolchain, downloaded once into `target/tmp/test-engine`: the first test run downloads `logix-core`, about 640 MB; `scripts/clean.sh` deletes it; CI caches it), `tests/sim.rs` (lint, test and simulate with the same real toolchain), `tests/format.rs` (format with the core's real `verible`, in the same engine folder), `tests/diagram.rs` (diagram with the real toolchain and elkjs, every family). `tests/designs/` holds small designs for tests and hand testing (not examples); tests copy them to a temporary folder. The ignored test `real_core_download` downloads the real core (about 640 MB): `cargo test --test packages -- --ignored`, and `real_download_packages_with_progress` does the same through MCP with progress: `cargo test --test mcp -- --ignored`. Run them after changing the manifest, the download code or progress reporting.
- **Before committing, run `scripts/test.sh`.** It ends by deleting build files unused for 7 days when `cargo-sweep` is installed (`cargo install cargo-sweep`), and dependencies build without debug info (`Cargo.toml`), since Cargo never deletes old build files: `target` had grown to 22 GB (5 GB fresh, 3 GB of it the test toolchain). After a deliberate schema change, run `scripts/update-schemas.sh` and review the diff in `schemas/tools.json`. The board schema is Logix Catalog's (`logix-board-v1.json`, address `catalog::BOARDS_SCHEMA`, also in `get_engine_info`'s `boards_schema`), owned and published by that repo; the engine's `CustomBoard` and `Resource` types must read every file it allows (a test checks the built-in catalog). Custom board files may name it, and a wrong `$schema` is a problem at its line.
- Rust is pinned in `rust-toolchain.toml`. With Homebrew's rustup, `cargo` is in `/opt/homebrew/opt/rustup/bin`, which isn't on the PATH by default. Every script sources `scripts/_rust-env.sh`, which adds it when `cargo` isn't found.

## CI and releases

**Repo type: installable** (topic `openlogix-installable`; the website repo's `CLAUDE.md`, Repo types, owns the policy): people install the engine for AI agents, and Logix IDE also downloads it as a dependency; a repo that's both is installable.

Same conventions as logix-ide, using the shared actions from `openlogix/.github` (`openlogix/.github/actions/<name>@main`; that repo documents and tests them).

- **`test.yaml`**: a `remote-config` job (Ubuntu) runs the shared `check-remote-config` action on `remote-config/` (platforms `darwin-arm64`; add the others with Milestones 3 and 4); then the tests. On every push and pull request, manually, and daily at 00:00 UTC; a newer run for the same ref cancels the older one; matrix macos-15, macos-26, macos-latest, `fail-fast: false`, 30 min. Installs the pinned Rust, then runs `scripts/test.sh`.
- **`build-pre-release.yaml`** (on every push to `main`, daily at 00:00 UTC, and manually; a newer run cancels a running one), three jobs:
  - `prepare` (Ubuntu): the shared `start-pre-release` action (today's tags, the stable-release check, `BUILD-INFO.json` as the `build-info` artifact, with `config-version`, read from `remote_config::CONFIG_VERSION`, as an extra field: `repos-janitor` finds the releases a Latest engine uses by it). The release tag is the engine version.
  - `build-darwin-arm64` (reusable `build-darwin-arm64.yaml`, macos-latest): `read-build-info` with the platform, checks out exactly `repo-commit` into `_repo/`, runs `scripts/test.sh`, builds with `LOGIX_ENGINE_BUILD_VERSION` = the release tag, packs `logix-engine-darwin-arm64-<package tag>.tgz` (one `logix-engine/` folder with the binary, `LICENSE-MIT` and `LICENSE-APACHE`), and checks that the packed binary reports the release tag and has an ad-hoc signature.
  - `pre-release` (Ubuntu): `read-build-info`, downloads the packages, virus scan, writes the release's own content (development builds, the macOS steps with `xattr -c`, trying it with `claude mcp add`, the packages table), then the shared `publish-pre-release` action writes the standard release text around it, makes the day's pre-release again from scratch with the `.tgz`, `BUILD-INFO.json` and `SHA256SUMS`, and deletes old pre-releases by the shared policy.
- Add Linux and Windows as `build-<platform>.yaml` and test matrix entries when those platforms are implemented.

## Rules that are easy to break

- **stdout is only for MCP.** Logs and tool output go to the log file and stderr, never stdout.
- **The tool API and command line never break** after the first release. Changes only add tools, optional fields or arguments. A breaking change gets a new tool name.
- **Stateless requests.** Every request carries its own folders and board. The engine never reads host project files or merges catalog definitions from disk, except the source files and the custom boards folder a request names. Requests never carry source text.
- **Safe file changes.** Check the path keyword rules, resolve symbolic links, and refuse forbidden locations before any disk change. The engine writes only in the engine folder and build folders, plus in-place rewrites of named source files when an operation calls for it, such as formatting, and generated files the request names, such as simulate's default GTKWave layout, replaced or deleted only while they carry the generated-file marker.
- **Build folders are disposable.** Deleting one never loses data, and the next operation that writes to it creates it again, with the same result. Never keep anything in a build folder that can't be generated again. A test checks a rebuild after a delete.
- **Match criteria are internal.** How a device's match level is decided never appears in the tool API, tool descriptions or messages to hosts, and can change in any version. Hosts get only the level (and later, an explanation for people to read as is).
- **Errors are data.** Use the six error categories and the suggested action codes from the tool API. A failing test or missed timing is a result, not an error. Messages never assume a particular host.
- **Schemas come from Rust types.** Don't hand-write JSON schemas. Every tool and field needs a clear, self-contained description, because AI agents learn the tools from them alone.
- **No network at startup, no unreported upgrades** (decided 2026-11-12, for remote updates). Network access happens only before an operation that needs packages, to fetch the engine's remote config when its cached copy is more than 24 hours old and to download or repair packages, or when a host asks (`check_updates`). An update is reported in the operation's progress and result, and `get_engine_info` lists the releases in use. `--no-auto-download` turns all of it off. The org rules are in the website repo's `CLAUDE.md`, Remote updates.
- **Development never affects end users** (the website repo's `CLAUDE.md`, the user's requirement for Milestone 2, 2026-11-12): try a remote config change with `LOGIX_ENGINE_DEV_REMOTE_CONFIG` (a branch's file, a fork or a local file), never by changing `remote-config/` on `main`, which every installed engine reads; it reaches users only by a pull request merged with CI green. A developer's own engine folders may be shared between dev and regular runs.
- **Date versions.** The engine follows the Open Logix versioning rule (the website repo's `CLAUDE.md`, Remote updates, Versions and tags): `yyyy-mm-dd` for tags and pins, `yyyymmdd` only in file names, `yyyy.mm.dd` for the version people see, semver (`2026.5.7`) only where a tool requires it, and at most one release a day. Compare by date, never as mixed-form strings.

## A reference for frontends

The Logix IDE is the reference frontend: the rule is in the website repo's `CLAUDE.md` (shared Open Logix rules). For the engine this means: logic every frontend would need, that doesn't depend on a frontend's own model, belongs here, such as FPGA family names (`get_catalog` families) plain resource names (`build` `resources_summary`), resource descriptions and checked shares (`build` `resources`, `src/build/descriptions.rs`; a share is null when nextpnr's numbers aren't valid, as Apio's report), clock names (`build` `clocks_summary`) and the build report's text (`build` `report` and `report_summary`, 2026-11-10; frontends show it as is). When the IDE has to repeat engine knowledge, that is an engine gap: fill it here and have the IDE use it. The tool API stands on its own for frontends outside Open Logix, and its "Recipes for frontend developers" point to the IDE files that implement each recipe.

**Canonical board** (the website repo's `CLAUDE.md` owns the rule, 2026-11-10): the engine's docs, tool descriptions and examples use the iCESugar v1.5 (`icesugar-1-5`) as their example board; the engine itself never favors it (catalog order, matching, defaults), except to break a tie. Examples that show captured hardware output, such as `list_devices` on an Alhambra II, stay as captured until they're captured again on an iCESugar. The tutorial (`docs/tutorial-claude-code.md`) uses the iCESugar v1.5 too (moved 2026-11-11, the user's decision, before the team had the board: its prompts are still to be tried on one). Tests may use any board.

## How work is done here

The human directs the work and tests the results. Claude writes and maintains the code, the tests and the docs. Humans don't review every line, so:

- Add or update tests with every change. Tests are the main guard against regressions.
- Keep external interfaces, requirements and docs simple and easy for people to understand. Code readability matters less than correctness and test coverage.
- Update the docs in `docs/` in the same change as the code they describe. If code and docs disagree, ask which one is right.
- Record open questions in the relevant doc's "Open questions" section, or as a GitHub issue if the user asks.
